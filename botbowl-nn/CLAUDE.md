# CLAUDE.md — botbowl-nn

Neural-network plumbing for the MCTS bot (plan 017): the **shared feature encoder**, the **offline prepare step**, and the **tract-onnx inference evaluator**. Depends on `botbowl-engine` + `botbowl-data`; **no** dependency on `botbowl-mcts` (mcts depends on nn, not vice versa). The PyTorch trainer lives outside the workspace in `../train/` (a `uv` project).

## The one rule: encoding lives here, in Rust, once

`encode.rs` is the **single source of tensor layout**, used verbatim by both the offline `prepare` bin and the live `NnEvaluator`. Python never parses a `GameState` — it only consumes the `.npy` batches `prepare` writes. This is deliberate: there is **no train/inference encoding skew** possible. If you change a channel, you change it here and the manifest's `spatial_channel_names`/`global_feature_names` update automatically; bump `NN_SCHEMA_VERSION` in `bin/prepare.rs`.

Shapes (schema v7): spatial `C=61` planes × `H` × `W`, global `F=18`, policy head `A=30`. `C` is **derived**, not a literal: `2 present + 8 shared per-player + Skill::COUNT + 12 shared`, so adding a `Skill` variant in `botbowl-engine/src/core/table.rs` widens the tensor automatically (the exhaustive `Skill::index` match makes forgetting `Skill::ALL` a compile error). It also invalidates every checkpoint's *shape* — bump `NN_SCHEMA_VERSION`, mirror the number in `train/src/bbnn/model.py`, rebuild both fixtures (`uv run python -m bbnn.fixture`, and the 14x7 goldens per `tests/capacity_parity.rs`) — **and register one step in `train/src/bbnn/migrate.py`** so trained weights carry over: `python -m bbnn.migrate old.pt --out new.pt --onnx new.onnx` detects the schema from the tensor shapes and applies each registered `Migration` in order, like a chain of commits. Inputs added at the end of a block are inserted as zero columns, so the migrated net computes exactly what the old one did until training moves them; every step is verified by running both nets on random inputs (`test_migrate.py` pins the chain is contiguous and exact). A step that cannot be function-preserving says `exact=False` and carries its own check. `H`/`W` are the **runtime `board_dims` including the 2-cell OOB border** — a `Position` indexes the tensor directly, and border cells are flagged by the `oob` plane and masked out of the policy (the network never emits masking; masking = "only gather legal actions", done identically in `eval.rs` and `train/model.py`).

**Per-player planes are unpaired; only `present` carries a side (schema v5).** A square holds at most one player (`add_new_player_to_field` rejects an occupied cell), so `us_present`/`them_present` already identify the owner and duplicating the other 47 per-player planes per side was pure redundancy — 103 channels became 56 (58 with the endzone planes below). It is lossless and recoverable in the *stem*: for binary planes `a` with `b = us_present`, `ReLU(a + b − 1.5)` is "us has `a`" and `ReLU(a − b − 0.5)` is "them has `a`"; for a characteristic `v`, `ReLU(v + b − 1)` is the mover's `v`. **That last identity needs `v ≤ 1`**, which is why the per-player normalisers are the engine's `PlayerStats::MAX_*` caps and not round numbers — `MOVE_NORM` was 10 against a real maximum of `MA + 2 = 11`, so movement_left encoded to 1.1 and the recovery silently stopped being exact. `per_player_planes_are_normalised_into_the_unit_interval` and `sampling_ranges_stay_under_the_engine_caps` are what hold that. The tackle-zone planes stay paired: they are neighbour counts, not attached to the player in the cell, and both teams can cover one square.

**`path_prob` is recomputed, never read from `state.path_buffer`.** The plane is the active player's per-square probability of arriving (the move's cumulative chance across every dodge, GFI and pickup), which the engine has already computed and cached — but that cache is `#[serde(skip)]` **and** `#[derivative(PartialEq = "ignore")]`. A state that has been through the corpus comes back with `has_paths == true` and an *empty* buffer, so an encoder that read it would emit an all-zero plane in training and a populated one at inference: silent skew, with the loss converging happily the whole time. Ignoring it in `PartialEq` is the second, independent problem — two states that recombine to one DAG node may hold different buffers, which would make the NN prior impure and break recombination. So the encoder calls `PathFinder::player_paths`, a pure function of `(state, id)`, and `recomputed_paths_match_the_engines_own_buffer` pins that it agrees with the engine's own buffer square for square. The `has_paths` gate *is* serialised and *is* in `PartialEq`, so gating on it stays pure. **This costs real time** — `encode` is ~3 µs without paths and ~50 µs with them (plan 038) — and **the cache is not a shortcut, even when it is populated**: at a `BlockAction` decision `has_paths` is true and the buffer holds direct-block offerings, not the mover's movement paths, so "read the buffer when present" would encode block decisions differently at inference than in the corpus. `the_engines_buffer_is_not_the_path_plane_at_a_block_decision` is the counter-example; leave it in. The cost is instead paid once per node, not twice, by the evaluation memo below.

It is also the one **lossy** plane: the pathfinder's `f32` is quantised to 1/255, floored at 1 so an unlikely path never reads as unreachable (`0` means exactly "no path"). `encode_raw` stores the quantised value and `encode` divides by 255, so the raw/normalised identity still holds bit-for-bit — the loss is at the input, not between the two views.

**Geometry is an input, not something to infer from the padding (schema v7, plan 042).** Two canonical-frame planes, `dist_to_us_endzone` (`x − 1`) and `dist_to_sideline` (`min(y − 1, h − 2 − y)`), and three globals, `playable_w / 26`, `playable_h / 15`, `team_size / 11`. Without them a translation-equivariant tower on one fixed board learns absolute position from its distance to the zero-padded edge, which is exactly what mixed-size training has to take away — and a pooled value head has no other way to know how long the pitch is. Absolute coordinate planes were rejected as the memorisable form. `geometry_planes_and_size_globals_follow_the_runtime_board` pins both under either mover.

**`us_td_zone` / `them_td_zone` are the only thing telling the net which way it attacks.** The tower is translation-equivariant and `oob` is symmetric in `x` (`is_out` is `x <= 0 || x >= width - 1`), so before these planes existed *nothing* in the tensor distinguished the scoring end from the conceding one — canonicalisation fixes the convention but cannot communicate it, and the policy head had no basis to prefer a move toward `x = 1` over the identical move toward `x = w - 2`. They are read from `dims.endzone_x` rather than hardcoded to the canonical column, so they cannot drift from the rules; `td_zones_are_canonical_for_either_mover` asserts they land on `x = 1` / `x = w - 2` under **both** movers, which doubles as an independent check on the `Away` x-mirror.

## Perspective is a single authority (`perspective.rs`)

`mover_for(state)` = `available_actions.team.unwrap_or(team_turn)`. Everything perspective-dependent — the encoder, the action↔cell map, the value sign — routes through here. **Canonical view: the mover attacks toward `x=1`.** `Home` already does (`endzone_x(Home)==1`) → encoded verbatim; `Away` is **x-mirrored** (`x → (width-1)-x`, no y-flip; involutive). The network's value `v` is **mover-centric** (`+1` = team-to-move winning); Home-centric is recovered by flipping sign for an `Away` mover.

The game's *other* mirror — across the pitch's long axis, `y → (H-1)-y` — IS a true symmetry of the *engine* (left/right of the attacking direction are interchangeable) and is exploited as **train-time random y-flip augmentation** in `train/src/bbnn/data.py` (`flip_y`; positional action cells flip y, simple/channel-max logits and value are invariant). Caveat: the *search's* collapsed chance model is not y-symmetric — every scripted bounce/scatter/deviate goes `Direction::up()` (`botbowl-mcts/src/roll_outcomes.rs`) — so policy targets near a sideline with a loose ball carry a small y-asymmetry the augmentation flips. Value targets come from real dice and are unaffected. Measured small (plan 023 y-control); plan 031 D7. The x-mirror is *not* a symmetry — it swaps attacking directions and is already spent on the canonicalisation above.

## Action ↔ policy cell (`actions.rs`)

Exhaustive matches pin `PosAT → 0..14`, `SimpleAT → 14..30`. Adding an engine action variant is a **compile error here** — a deliberate trip-wire forcing a schema bump. Positional actions target one canonicalised cell `(channel, y, x)`; simple actions have no cell and their logit is the channel-wide spatial **max**.

## Targets (`targets.rs`) — never train π on raw visit counts

`recon_mcts` freezes a solved child's visits, and the fastest-solving child is often the *best* move, so `π ∝ visits` is wrong (plan 017 §caveat). `policy_target`: root solved → one-hot on argmax mover-`Q` (or `Skip`); partially solved → visits, but the argmax-`Q` solved child is floored at the max unsolved-sibling visit count; else normalise visits. All `Q` comparisons are in the **mover's** frame (`Away` negates the Home-centric stored `Q`). `value_target` = mover-signed outcome `z`. `policy_target_of(.., PolicyTargetKind::CompletedQ { tau })` (plan 032 #7; `prepare --policy-target cq --tau 100`) is the Gumbel-style alternative for unsolved roots: `softmax(ln prior + q_mover/τ)`, children with no `Q` or zero visits completed by the visit-weighted mean `Q` of the visited ones; solved roots stay one-hot. The prior's global scale cancels in the softmax, so heuristic and NN corpora both work. `scripts/audit_q_target.py` holds the reference Python implementation (agrees to 3e-8) and scores any target against the 16k convergence reference.

## prepare (`bin/prepare.rs`)

`prepare --in *.jsonl --out DIR [--solved-root onehot|skip] [--min-root-visits N] [--policy-target visits|cq --tau T]`. Streams `DatasetReader`, groups samples **by board dims** (one `dims_{w}x{h}` subdir each → fixed-shape batches for free; since plan 042 the trainer's `open_prepared(DIR)` reads *all* of them with a per-board batch sampler — never `head -1` a `dims_*` listing), writes `spatial/global/value/chosen` `.npy` + a **CSR** ragged legal-action encoding (`actions.npy (M,4)`, `policy.npy (M,)`, `action_offsets.npy (N+1,)`) + `manifest.json`. `npy.rs` is a hand-rolled `.npy` v1.0 writer/reader (avoids the ndarray stack).

**Peak RSS is O(1) in corpus size, and must stay that way.** `spatial` is 8,496 bytes/sample at C=59 (it was 21,312 at C=37/f32: the u8 corpus and the unpaired per-player planes together more than paid back the 6→39 skill widening); buffering it cost 2.03 GB of RSS for one generation and OOM-killed `prepare` at a 3-generation window on the 14.4 GB training box. The corpus-sized arrays now go straight to disk through `npy::StreamWriter`, which reserves `STREAM_HEADER_RESERVE` (128) bytes, streams rows, then seeks back and back-patches the header once `N` is known — legal because a v1.0 header's length depends only on dtype+shape, and byte-identical to the buffered writer for every shape `prepare` emits (all of them pad to 128; `finish` asserts if one ever wouldn't fit). A two-pass "count then write" was rejected: parsing is most of the runtime. Only `value`/`chosen`/`offsets` stay in RAM (~20 B/sample). Measured on gen00's 6 train shards (99,059 samples, at C=37/f32): 2,134,156 kB → 8,984 kB peak, output md5-identical.

**`spatial.npy` is `u8` raw counts, not pre-normalised `f32` (schema v4).** Every spatial channel is an integer quantity — a flag, a characteristic, a tackle-zone count — so `u8` is *exact*, not a quantisation, and `encode_raw` is the source of truth with `encode` defined as `encode_raw / spatial_channel_scales()`. That identity is pinned bit-for-bit by `raw_u8_planes_reproduce_the_normalised_ones_exactly`. The scales ride in the manifest as `spatial_scales` and `train/src/bbnn/data.py` divides by them; **never hardcode them in Python** — that is the one place train/inference skew can still get in, which is why a manifest without them is a hard error rather than a default. The live path (`eval.rs`, `remote.rs`) is untouched and still f32: the win is disk and dataloader, not inference. Quantising the *socket* payload was considered and rejected — `movement_left/10` is not u8-representable, so it would break the `< 1e-3` tract-parity canary.

## eval (`eval.rs`) — frozen NN, pure function of state

`NnEvaluator::from_path` loads ONNX; the model has dynamic `H`/`W`, so we build one tract runnable **per `(H,W)`** on first use and cache it (board dims are constant per game → one entry). `priors(state, &actions)` = one forward, gather per-legal-action logits (positional cell / simple channel-max), softmax in Rust, **rescale ×`len`** so mean prior ≈ 1.0. `value_home_i64(state)` = mover-centric `v`, clamped to `[-1,1]`, sign-flipped Home-centric, **×1000** (matches `leaf_score`'s TD = ±1000). A frozen deterministic CPU net is a **pure function of state** → recombination-safe. The ×1000 and ×K rescales are calibration bridges coupled to `PUCT_C`/`leaf_score` in `botbowl-mcts`.

**One encode and one forward per node (`LAST_FORWARD`).** The search scores a node, then asks for its priors, on the same state and thread; a thread-local slot serves the second call. It is **keyed on the `GameState` under `PartialEq`** — the identity `StoreState` recombination uses, and stricter than the encoded tensor since the encoder reads nothing `PartialEq` ignores. Never a hash (the `HashOnly` lesson), and no longer the tensor: comparing tensors meant running the encoder, pathfinder included, just to build the key. `tests/memo.rs` pins one forward per node and hit ≡ fresh evaluation; `examples/encode_bench.rs` is the microbenchmark. Measured ~70–100 µs less non-NN time per forward, ~10% end-to-end on the sidecar (plan 038 §Open items).

## remote (`remote.rs`) — the batched sidecar backend (plan 024)

`NnEvaluator` has two backends. **tract is the default and the numerics reference**; `Backend::Remote` forwards to `scripts/nn_server.py` over a Unix socket and **always carries a tract fallback**, so an absent/dead/wedged server makes a shard *slow*, never broken (one `NN_SERVER_FALLBACK` warning, count printed at exit). Turn it on with `--nn-server PATH` on `dataset`/`eval`, or `BLOOD_NN_SERVER`; unset ⇒ byte-identical to before, no GPU, no new Cargo dependency, works on a Mac.

- `forward_raw` (+ the value-only sibling) is the **single dispatch point** — `priors`, `value_home_i64` and both `botbowl-mcts/src/dynamics.rs` call sites are untouched and nothing is async. `value_home_i64` sets `want_policy = false`, cutting the response from 17 KB to 4 B (that's the generator's whole traffic).
- **The canary handshake is a safety interlock, not a smoke test.** A connection is bound to one model; the server returns *that model's* result on the committed `parity_9x16_*` fixture and the client compares to its own tract answer at `< 1e-3`, aborting the process on mismatch. Serving the wrong weights is otherwise undetectable — it produces a plausible corpus, or a plausible promotion-gate verdict, labelled with the wrong net. The `model_id` echo check on every request is the second, independent guard.
- One connection per (thread, evaluator) via `thread_local!`, so the client is `Sync` without a lock and the eval phase's two nets share one socket without cross-talk.
- Numerics: torch-CUDA vs tract agree to ~1e-5 in practice; the contract is `< 1e-3` for remote-vs-tract and `< 1e-5` for batch invariance (`tests/remote.rs`). `tests/parity.rs` keeps its 1e-4 tract-vs-PyTorch assertion **unchanged** — tract is still the reference.
- `BLOOD_NN_PROFILE=1` prints `NN_PROFILE forwards=… share=…` per game and at exit: the forward counter that measured the 85% inference share behind plan 024.
- **Model identity, server-side, is the resolved `.pt` file — never the client's path string.** Two spellings of one net (`models/x.onnx` vs an absolute path) must share a `model_id` and a batch queue; keying on the string rejects the second spelling at `--max-models 1`, or loads the net twice and halves the batch above 1. Both fail silently, as lost speed. Pinned by `live_server_identifies_a_model_by_its_weights_not_its_path_string`.
- **Batches are padded up to a CUDA-graph bucket, which is sound only because BatchNorm is in `eval` mode** — rows are independent, so a padding row cannot reach a real one. `live_server_is_batch_invariant` is what pins that, and it is the test to check first if anyone ever touches `.eval()` or the graph pool. It compares `max |v − reference|`; an earlier version compared `max(0.0, v)` and was vacuous for any net with negative values.
- Throughput: `--nn-server --parallel-games 4` measured **3.79× end-to-end** against tract, at **4.3× less CPU per forward** (plan 024 §Measured results, stages 3–5). tract is internally multi-threaded and was the CPU hog, not just the latency.
- **Server shape (plan 033, 2026-09-09):** `nn_server.py` is a *single-threaded* `selectors` loop with a depth-2 GPU pipeline (launch batch N+1 while batch N's result is read back) — no per-connection threads, no `Queue`. The GPU's own work for a batch of 1–4 is ~300 µs of cuDNN kernels on a 16x9 board and is the floor; everything else was host overhead. Per-request latency at 6 clients went 1.37 → 0.91 ms (idle box), server CPU 77 → 65 %. Two traps if you touch the loop: `epoll` rounds sub-ms sleeps up to 1 ms (use `SelectSelector` + a short spin), and without `cudnn.benchmark=True` the b=1 graph bakes in a 4 ms algorithm. `examples/nn_bench.rs` is the round-trip benchmark (`--server SOCK --threads N`); `train/tests/test_nn_server.py` is the protocol test on CPU.

## Parity fixture

`tests/fixtures/tiny.onnx` + `parity_{h}x{w}_*.npy` are **committed** (built by `train/src/bbnn/fixture.py`). `tests/parity.rs` (not `#[ignore]`d) asserts tract == PyTorch to `< 1e-4` at two board sizes — this is what de-risks tract op coverage (Expand/Shape broadcast, ReduceMean, BN fold, dynamic axes). Rebuild the fixture after any `model.py` architecture change: `cd train && uv run python -m bbnn.fixture`.

```sh
cargo test -p botbowl-nn                 # unit + prepare integration + parity
cargo run -p botbowl-nn --bin prepare -- --in data/*.jsonl --out data/prepared/x
```
