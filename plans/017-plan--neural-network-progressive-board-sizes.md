# Training neural network on progressively bigger boards

We currently have a heuristic to evaluate leaf nodes and a simple scripted thing for action priors. In this idea we do
what alpha zero did and have a neural network calculate the priors and the leaf node values.

The network priors will estimate the visit counts of the children of a node after mcts search. The leaf node value will
estimate which team scores at the end of the drive, -1 for opponent, 0 for no score, 1 for one-self.

The network will be trained on the data generated by mcts search.

## Progressive training on larger board

We'll use a network architecture that can run on any board size so we can start training on smaller boards with fewer
players. This allows the network to learn the basic mechanics of the game without in a reward-rich environment.

Here's a suggestion for how the size can progress. Note that the witdh of the board is always odd and rougly half of the
height. And the end zone is always at height 0 and height -1. And the height is always even.

| Board size (W x H) | Players | LoS players | Max wing | player MA |
| ------------------ | ------- | ----------- | -------- | --------- |
| 26\*15             | 11      | 3           | 2        | 6         |
| 20\*11             | 7       | 3           | 1        | 6         |
| 14\*7              | 4       | 2           | 0        | 4         |
| 8\*3               | 2       | 1           | 0        | 2         |

Note that in fact we'll add 2 to the height and width to account for the out-of-bounds squares.

## Engine precondition: configurable board size

The pitch dimensions and team size are currently `pub const` in `model.rs`, and `FullPitch<T>` bakes them into a
stack-allocated `[[T; HEIGHT]; WIDTH]`. To support the progression we switch to a build-time selection: a `build.rs`
reads three env vars — `BOARD_SIZE_W`, `BOARD_SIZE_H`, `BOARD_PLAYERS` — and emits the constants. Each curriculum tier
is a separate `cargo build`. Keeps the const-array hot path, no runtime indirection, no generic-parameter infection
through `GameState` and every procedure.

Derived constants (LOS x, LOS y-range, north/south wing y-ranges, default setup positions, ball off-pitch checks) become
expressions of W/H rather than hand-tuned literals. See the table above which can be hardcoded in `build.rs` and emitted
as constants, or computed from the base dimensions with some heuristics.

Setup-legality rules (min 3 on LOS, max 2 per wing) and parts of the kickoff procedure assume 11-on-11 and a real
formation; on small tier we drop the wing constraints and use a simpler setup. Gated on `BOARD_PLAYERS` rather than a
runtime tier flag so the smaller binary doesn't even compile the formation-check code paths.

Kickoff scatter and throw in dice need to be adjusted both in `ball_procs.rs`. The cleanest solution is to hard-code
which kind of requested roll we use. The distance dice in kickoff scatter and throw in can never be more than `WIDTH/2`
or it risks landing the ball out of bounds too often.

### Migration steps

Mechanical (do first, low risk):

- `build.rs` reads `BOARD_SIZE_W` / `BOARD_SIZE_H` / `BOARD_PLAYERS`, emits the `WIDTH` / `HEIGHT` / `TEAM_SIZE` consts.
  Defaults reproduce the current 28 / 17 / 11.
- Replace LOS x literals (`14`, `13` in `model.rs`) with `WIDTH/2`, `WIDTH/2 - 1`.
- Replace `11.min(...)` and `> 11` checks in `gamestate.rs:1299-1302` with `TEAM_SIZE`.
- Replace `.take(11)` in `kickoff_procs.rs:198` with `.take(TEAM_SIZE)`.
- Clamp kickoff aim (`gamestate.rs:735-737`) so `WIDTH/4` can't land on or behind the end zone on narrow boards — e.g.
  `max(2, WIDTH/4)`.
- Scale roster construction (`gamestate.rs:79-90`) so the 6/2/2/2 role distribution becomes a function of `TEAM_SIZE`.
  For tier 1 (1 player) we just build one lineman.

Decisions to make (these are curriculum design, not refactors):

- **LOS y-span policy.** `LINE_OF_SCRIMMAGE_Y_RANGE = 5..=11` is "middle 7 cells" by convention, not by formula. On
  HEIGHT=6 a 7-wide span can't fit. Options: (a) `min(7, HEIGHT-2)`, (b) "entire non-endzone column" on small tiers, (c)
  drop the LOS concept entirely below some tier. Mirror the choice for north/south wings.
- **Setup formation on small tiers.** The SetupLine template in `kickoff_procs.rs:230-233` has fixed per-role x-offsets
  (thrower at +6 from LOS, catcher at +2). On WIDTH ≤ ~7 the thrower offset puts them off-pitch and the current code
  silently skips them. Either (a) provide a compact formation per tier, (b) compute offsets as
  `min(default, half_width-1)` and accept that roles collapse together, or (c) skip SetupLine on small tiers and only
  allow manual placement.
- **What does "kickoff" mean with 1-2 players?** Kickoff-table events (Perfect Defense, Blitz!, Quick Snap, …) all
  assume a real formation. Cheapest path: gate the kickoff table on `BOARD_PLAYERS >= N` and use a degenerate kickoff
  (ball spawns somewhere, both teams in place) below that threshold. N is a curriculum choice — probably 7 or so.
- **Role distribution per tier.** 1-player and 11-player tiers are obvious; 3 / 5 / 7 / 9 are not. Pick a default early
  so lectures stay comparable across runs.

### Open questions

- **Test strategy.** ~40+ tests in `gamestate.rs` and `pathing.rs` hardcode coordinates like `(10, 8)` that OOB-assert
  on small boards. Rewriting them all to be size-generic is high-cost and most pin behaviors that only exist on the full
  pitch (e.g. specific LOS / wing rules). Answer: attempt to re-write the hard coded coordinates so they work on all
  board sizes it makes sense to run the test on. For the test that require large dimensions we have a mechanism to skip
  them if testing on a too small board.
- **Cross-tier weight transfer.** Tower weights transfer cleanly (it's a fully-conv stack). The value head is a pooled
  scalar, also fine. The policy head has a non-spatial branch whose output dimension is the number of non-spatial verbs
  — verify that's stable across tiers (it should be: reroll, end turn, etc., don't depend on board size) and that the
  spatial-policy head's per-cell output transfers naturally to bigger pitches.
- **Curriculum promotion criteria.** When do we stop training tier K and move to tier K+1? Win rate vs. scripted bot?
  MCTS-vs-MCTS-without-prior comparison? Plateau detection on the value head's validation loss? Pick one before starting
  so we're not re-deciding mid-run. Answer: defer this to later. Let's manually check this to begin with.

## Network architecture

The constraints on the network are:

- It should be able to run on any board size.
- It will take spatial and non-spatial features as input. Non-spatial features include things like turns left of the
  half. Spatial features include the position of the players and the ball.
- It needs to be able to produce priors for spatial actions (verb + coordinate, `move(x, y)`) and non-spatial actions
  (only verb, `use_reroll`).
- It needs to be able to produce a leaf node value for the current state.

Given these constraints we have many options, here are a few that can be evaluated:

- Fully convolutional network with global pooling for non-spatial features and separate heads for priors and value.
  - Concretely: AlphaZero-style residual conv tower (N blocks of `Conv3x3 → BN → ReLU → Conv3x3 → BN → (+skip) → ReLU`,
    same channel count throughout, no flatten). Policy head is a 1x1 conv for per-cell spatial priors plus a small dense
    branch off pooled features for non-spatial verbs; value head is global-average-pool → MLP → scalar. Skip connections
    are what make a deep tower trainable; depth controls receptive field (~(2N+1) cells), so pick N to cover the full
    15x26 pitch.
- A transformer-based architecture that can handle variable input sizes and produce the required outputs.

## Trade-offs

Scoring the leaf node on who scores at the end of the drive isn't necessarily counting towards winning the game. A
skilled human can easily exploit this behaviour to do a 2-1 grind. But it's a lot easier to train a network this way so
we'll start there.
