# Training neural network on progressively bigger boards

We currently have a heuristic to evaluate leaf nodes and a simple scripted thing for action priors. In this idea we do
what alpha zero did and have a neural network calculate the priors and the leaf node values.

The network priors will estimate the visit counts of the children of a node after mcts search. The leaf node value will
estimate which team scores at the end of the drive, -1 for opponent, 0 for no score, 1 for one-self. The network will be
trained on the data generated by mcts search.

## Progressive training on larger board

We'll use a network architecture that can run on any board size so we can start training on smaller boards with fewer
players. This allows the network to learn the basic mechanics of the game without in a reward-rich environment.

Here's a suggestion for how the size can progress. Note that the witdh of the board is always odd and rougly half of the
height. And the end zone is always at height 0 and height -1. And the height is always even.

| Board size (W x H) | Players | LoS players | Max wing | player MA |
| ------------------ | ------- | ----------- | -------- | --------- |
| 26\*15             | 11      | 3           | 2        | 6         |
| 20\*11             | 7       | 3           | 1        | 6         |
| 14\*7              | 4       | 2           | 0        | 4         |
| 8\*3               | 2       | 1           | 0        | 2         |

Note that in fact we'll add 2 to the height and width to account for the out-of-bounds squares.

## Engine precondition: configurable board size (implemented in `build.rs`)

It's now possible to configure the board size at compile time as well as with env vars, or even when creating the game
state.

### Open questions

- **Cross-tier weight transfer.** Tower weights transfer cleanly (it's a fully-conv stack). The value head is a pooled
  scalar, also fine. The policy head has a non-spatial branch whose output dimension is the number of non-spatial verbs
  — verify that's stable across tiers (it should be: reroll, end turn, etc., don't depend on board size) and that the
  spatial-policy head's per-cell output transfers naturally to bigger pitches.
- **Curriculum promotion criteria.** When do we stop training tier K and move to tier K+1? Win rate vs. scripted bot?
  MCTS-vs-MCTS-without-prior comparison? Plateau detection on the value head's validation loss? Pick one before starting
  so we're not re-deciding mid-run. Answer: defer this to later. Let's manually check this to begin with.

## Network architecture

The constraints on the network are:

- It should be able to run on any board size.
- It will take spatial and non-spatial features as input. Non-spatial features include things like turns left of the
  half. Spatial features include the position of the players and the ball.
- It needs to be able to produce priors for spatial actions (verb + coordinate, `move(x, y)`) and non-spatial actions
  (only verb, `use_reroll`).
- It needs to be able to produce a leaf node value for the current state.

Given these constraints we have many options, here are a few that can be evaluated:

- Fully convolutional network with global pooling for non-spatial features and separate heads for priors and value.
  - Concretely: AlphaZero-style residual conv tower (N blocks of `Conv3x3 → BN → ReLU → Conv3x3 → BN → (+skip) → ReLU`,
    same channel count throughout, no flatten). Policy head is a 1x1 conv for per-cell spatial priors plus a small dense
    branch off pooled features for non-spatial verbs; value head is global-average-pool → MLP → scalar. Skip connections
    are what make a deep tower trainable; depth controls receptive field (~(2N+1) cells), so pick N to cover the full
    15x26 pitch.
- A transformer-based architecture that can handle variable input sizes and produce the required outputs.

### First architecture to try: CNN Tower

Given the game state object we produce spatial features as a 3D tensor of shape `(C, H, W)` where C is the number of
channels (features), H is the height of the board, and W is the width of the board. Non-spatial features are a 1D tensor
of shape `(F,)` where F is the number of non-spatial features. We process the non spatial features through one dense
layer to produce another vector of shape `(F',)` where F' is the number of features after processing. We then
concatenate the processed non-spatial features to the spatial features and feed them into a series of convolutional
layers. So the dimension of the input to the convolutional layers is `(C + F', H, W)`. The output of the convolutional
layers is then fed into two separate heads: one for the priors and one for the value.

The priors head produces a tensor of shape `(A, H, W)` where A is the number of actions (spatial + non-spatial). The
prior for a spatial action is the value at the corresponding cell in the tensor. The prior for a non-spatial action is
the max value across all cells in the corresponding channel of the tensor (we can consider averaging instead of max, but
max is more consistent with the idea of "prior" as a preference). Then to get a distribution that that sums to 1, we can
apply a softmax across the A channels for each cell but first we need to mask out the invalid actions. I think the
easiest way to do this is to set the logits of the invalid actions to a very negative number (e.g. -1e9 or -inf) before
applying the softmax.

The value head shall produce a single scalar value. As input it gets the output of the convolutional layers, which is a
tensor of shape `(C', H, W)` where C' is the number of channels where H and W can be vary depending on the board size.
We apply one or more CNNs for the value head and then apply global average pooling to get a single vector of shape
`(C',)`. This vector is then fed into a dense layer to produce the final scalar value.

## Trade-offs

Scoring the leaf node on who scores at the end of the drive isn't necessarily counting towards winning the game. A
skilled human can easily exploit this behaviour to do a 2-1 grind. But it's a lot easier to train a network this way so
we'll start there.

## Caveat (2026-07-13): solved-subtree pruning distorts visit counts — don't train π on raw N

This plan states that "the network priors will estimate the visit counts of the children of a node after mcts search".
Since commit `bc687b9`, that statement is no longer safe to implement literally: `recon_mcts` marks exhausted subtrees
**solved** (terminal, or all children solved) and removes them from selection. A solved child's visit count _freezes_
while unsolved siblings keep accruing — and the child that solves fastest is frequently the _best_ one (a touchdown move
solves in ~10 descents at Q≈1000 while mediocre siblings keep collecting visits). Under solved pruning, `N(a)` at the
root means "exploration effort spent", not "posterior preference"; the best move can have the lowest visit count. This
distortion applies even when the root itself never solves (typical for full-size games) — any partially solved root
child skews the distribution. Action _selection_ is unaffected (`MctsBot` picks by aggregated Q, which over a solved
subtree is exact minimax), but AlphaZero-style policy targets `π ∝ N` would be actively wrong.

When building the self-play data generator, read the solved flag instead of blindly normalising visits (expose per-child
solvedness through `get_next_move_info` at that point):

1. **Root solved** → one-hot (or low-temperature softmax) over the exact child Q values. A solved root is a proven
   position; the sharp target is correct — arguably better supervision than a fuzzy visit distribution. (Alternatively:
   skip solved-root positions as policy samples entirely; they are trivially decided.)
2. **Root partially solved** → hybrid target: visits for unsolved children; for solved children, substitute a
   pseudo-count (at minimum: if the solved child is the argmax-Q child, give it at least the max sibling visit count).

Upside for the value head: solved nodes carry _exact_ minimax values within the horizon — a gold-standard value target,
cleaner than bootstrapping from the game/drive outcome.
